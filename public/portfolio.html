Problem
The v1.0 spec covered the API calls and little else. Getting from "create" to a shell meant polling for status and looking up an address, every command needed a server ID, and nothing double-checked a delete.
Approach

National Consortium for Drone Security · 2025–26

AIDrone: reading a drone's control link byte by byte

Built and flew a research drone, then decoded the frames it sends and receives.

I traced the drone's SDK down to raw bytes to map its 20-byte command and telemetry frames, then analyzed its Wi-Fi video traffic in Wireshark.

20bytes in every frame, header to checksum

2links analyzed: serial control and Wi-Fi video

3AI features on board: face, gesture, voice

Read moreShow less
Problem
To secure a drone's control link you first need to know exactly what travels over it, down to the byte, and the SDK only exposes it as function calls.
Approach
I assembled the drone, set up Raspberry Pi OS with the Pi as a Wi-Fi access point, and wrote Python keyboard control on the pyaidrone SDK for takeoff, landing, movement, altitude and yaw, plus Scratch automation. To see the control link, I traced the SDK's packet builder and stream parser down to raw bytes. Commands go over USB serial to the radio dongle as fixed 20-byte frames, streamed continuously. The parser is a small state machine: it hunts for a 4-byte header, collects the frame and checks its checksum. For the Wi-Fi link, I captured traffic in Wireshark during live camera streaming and found the MJPEG video stream over TCP. Its spurious retransmissions came from delayed ACKs and showed where the link's latency limits were. Face and gesture recognition, automated photo capture and on-device wake-word voice control came after.
Outcome
A field-by-field map of the command and telemetry frames, and a drone that flies from Python, Scratch or voice commands, with face and gesture recognition on board.

Problem

Approach

EMMA, a real-time gravity engine

An N-body sandbox where orbits stay stable because the integrator conserves energy.

Velocity Verlet on a fixed timestep keeps the energy steady, and a Barnes-Hut quad-tree cuts the force step from O(N²) to O(N log N).

30 = 144FPS, identical physics at both

N log Nforce step, with a Barnes-Hut quad-tree

11stars on GitHub

Read moreShow less
Problem
Simple N-body demos step with Euler, which leaks or adds energy every frame, so orbits spiral apart and the physics changes with the frame rate. They also compute the force between every pair of bodies, which gets slow as the count grows.
Approach
I integrate with velocity Verlet on a fixed timestep, soften gravity at short range so close encounters don't blow up, and merge colliding bodies while conserving mass and momentum. A Barnes-Hut quad-tree treats distant groups of bodies as single masses, so each force step costs O(N log N) instead of O(N²). Presets load the figure-eight three-body orbit and a triple system. A HUD shows total energy as a live correctness check, and an ImGui panel spawns bodies with a chosen mass, speed and direction.
Outcome
Orbits come out the same on any machine and at any frame rate.

Universe Splitter

A Many-Worlds decision maker that picks between two weighted options using quantum randomness.

It queries seven randomness sources at once through a Cloudflare proxy and hashes every answer with SHA-256 into one draw.

7sources queried per draw

4of them quantum

1honest source is enough

Read moreShow less
Problem
The app's premise needs a draw from physical quantum sources, and any single public source can be offline or untrustworthy.
Approach
The app queries all sources at once through a same-origin Cloudflare proxy, which keeps API keys on the server and spares the browser any cross-origin calls. It hashes the responses together with SHA-256. If nothing answers, it falls back to crypto.getRandomValues and labels the result "not quantum".
Outcome
The draw stays unpredictable as long as any one source is honest. Nothing the user types leaves the browser.

Note · face anonymization project

Why I checked every frame

The part of the face anonymization project I didn't enjoy was evaluation.

At Soonchunhyang University's lab, we built a program to hide witnesses' identities in video. Instead of blurring, it replaces parts of the face and changes features like hair and eye color, so the witness looks like a completely different person. The program never stores the original face, and whoever holds the key can run the transformation backwards. I was a developer on it, using OpenCV, MediaPipe and PyQt5.

But for a bit more than two months, most of my time went into running the pipeline over test footage, checking frame by frame where a face was missed or the swap glitched, and checking that the restored face matched the original. And the cases that mattered most, faces turned to the side, partly covered, or badly lit, were rare in our data.

I kept at it because of what a miss costs. If the system loses a witness's face for even a few frames, their identity is exposed.

One clear frame is enough to recognize someone.

Our data was imbalanced, so a model could score very well and still miss exactly those frames. Only the frame-by-frame checking caught that.

I still prefer building to measuring. But I stopped treating evaluation as the boring part, because it's the only part that tells you whether the thing is safe to ship.
